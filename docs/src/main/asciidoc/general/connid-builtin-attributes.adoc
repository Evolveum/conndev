= ConnId Built-in (Special) Attributes: Value-Type Requirements and Handling

[abstract]
== Abstract

ConnId reserves a set of *special attribute names* (the "built-in" attributes) with
the `pass:[__NAME__]` naming convention. They carry framework-level semantics:
identification (`pass:[__UID__]`, `pass:[__NAME__]`), account state
(`pass:[__ENABLE__]`, `pass:[__LOCK_OUT__]`, dates), credentials
(`pass:[__PASSWORD__]`), group membership, and auxiliary object classes.

This document answers three questions:

. Which of these attributes have *specific value-type requirements*?
. How must a *connector* (generic ConnId SPI, and the conndev low-code DSL) handle them?
. How does *midPoint* handle them when it consumes a ConnId resource?

Sources explored:

* ConnId 5.x `connector-framework` — `org.identityconnectors.framework.common.objects`
* midPoint `provisioning/ucf-impl-connid` (ConnId UCF implementation)
* midPoint `infra/schema` (`resource-schema-3.xsd`, `SchemaConstants`)
* conndev `base` module (`com.evolveum.polygon.conndev`)

NOTE: The classic ConnId 1.x/2.x `BuiltinAttributes` interface was superseded.
In the current API the special names live in `Name`/`Uid`, `OperationalAttributes`,
`PredefinedAttributes` and their corresponding `...Infos` classes.

== Naming Convention

All special attribute names are built by
`NameUtil.createSpecialName(name)` (`NameUtil.java`): a name wrapped in
double underscores — `pass:[__]` + name + `pass:[__]`. For example
`"ENABLE"` becomes `pass:[__ENABLE__]`.

* `AttributeUtil.isSpecial(attr)` / `isSpecialName(name)` return `true` for any
  `pass:[__...__]` name.
* Attribute-name matching is *case-insensitive* (`NameUtil.namesEqual`).
  `pass:[__enable__]`, `pass:[__ENABLE__]` and `pass:[__Enable__]` are the same attribute.
* `AttributeUtil.getBasicAttributes()` / `getSpecialAttributes()` partition an
  attribute set into plain vs. special attributes.

== Built-in Attribute Catalog

The complete set of built-in attributes, their required value types, flags,
and where the framework defines them.

NOTE: "Enforced" = whether the ConnId framework *rejects* a wrong type at runtime
(see "Enforcement Tiers" below). Everything else is a *convention*: the framework
will accept it, but midPoint (and the framework's own accessors) expects the
documented type.

Hard rules (the framework throws):

* `Uid` constructor rejects blank values (`Uid.java`, `check()`).
* A `ConnectorObject` *must* contain a `Uid` instance and a `Name` instance —
  plain `Attribute` objects with those names are rejected
  (`ConnectorObject.java`, constructor).
* `pass:[__UID__]` must not appear in the connector `Schema` nor in the attribute
  set of a `create()` call. The `create()` result (the returned `Uid`) is the
  only way the client learns the UID.
* `Uid` optionally carries `revision` (MVCC string) and `nameHint` (last known
  `Name`) — both plain strings, `nameHint` used to disambiguate/rename reliably.

Date convention: the `AttributeInfo` javadoc recommends representing dates as
`long` in UTC. The accessors in `AttributeUtil` confirm the runtime types:

* `AttributeUtil.isEnabled()` / `isLockedOut()` / `getPasswordExpired()` →
  `Boolean` (via `getBooleanValue`)
* `AttributeUtil.getPasswordExpirationDate()` / `getEnableDate()` → `Date` built
  from a `long` (via `getLongValue`/`getDateValue`)
* `AttributeUtil.getPasswordValue()` / `getCurrentPasswordValue()` →
  `GuardedString` (via `getGuardedStringValue`)

== Enforcement Tiers

What does the framework actually *enforce* vs. what is convention?

=== Hard-enforced (framework throws)

`pass:[__PASSWORD__]` / `pass:[__CURRENT_PASSWORD__]` type::
  `AttributeInfo` must declare `GuardedString.class`, else `IllegalArgumentException("Password based attributes must be of type GuardedString.")` — enforced in `AttributeInfo.java` (constructor)

`pass:[__PASSWORD__]` / `pass:[__CURRENT_PASSWORD__]` value::
  must be single-valued and the value must be a `GuardedString` instance, else `IllegalArgumentException` — enforced in `Attribute.java` (constructor)

`pass:[__UID__]` value::
  must be non-blank `String`, else `IllegalArgumentException` — enforced in `Uid.java`

Object identification::
  `ConnectorObject` requires `Uid` and `Name` *instances* (not plain attributes) — enforced in `ConnectorObject.java` (constructor)

Any attribute type (schema)::
  must be one of the supported types (`FrameworkUtil.checkAttributeType`): `String`, `long/Long`, `char/Character`, `double/Double`, `float/Float`, `int/Integer`, `boolean/Boolean`, `byte/Byte`, `byte[]`, `BigDecimal`, `BigInteger`, `GuardedByteArray`, `GuardedString`, `Map` (+subtypes), `ZonedDateTime`, `ConnectorObjectReference`, `EmbeddedObject` — enforced in `FrameworkUtil.java`

Flag consistency::
  `NOT_READABLE` without `NOT_RETURNED_BY_DEFAULT` is rejected — enforced in `AttributeInfo.java` (constructor)

=== Conventional (not type-checked by the framework)

* `boolean` / `long` / `String` types of the other operational and predefined
  attributes are *not* validated by the framework. A connector that returns a
  `String` for `pass:[__ENABLE__]` or an `Integer` for `pass:[__ENABLE_DATE__]`
  will pass the framework, but:
** the `AttributeUtil` accessors throw `ClassCastException` when the type is read
   through them, and
** midPoint's conversion code casts to `Boolean` / `Long` / `GuardedString`
   (`MiscUtil.castSafely`, `getRealValue(...)`), so the value is dropped or the
   read fails.
* `pass:[__SHORT_NAME__]` and `pass:[__DESCRIPTION__]` have no declared standard
  type; `String` is the universal practice.

IMPORTANT:: The *only* built-in attributes with hard value-type requirements are
the password attributes (`GuardedString`) and the identification attributes
(non-blank `String` UID, required `String` NAME). All other type requirements
are conventions defined by the standard `AttributeInfo`s — and midPoint depends
on them.

== Date Value Types: `long` vs `ZonedDateTime`

`ZonedDateTime` is a fully supported ConnId attribute type (`FrameworkUtil.ATTR_SUPPORTED_TYPES`),
and midPoint maps it to `xsd:dateTime` in the generated resource schema
(`XsdTypeMapper` — `ZonedDateTime.class` → `xsd:dateTime`). Whether you should
*use* it depends on whether the attribute is a built-in one.

=== Regular attributes: `ZonedDateTime` is supported end-to-end

schema::
  `ZonedDateTime` → `xsd:dateTime`; the shadow attribute is typed `XMLGregorianCalendar` — in `ConnIdTypeMapper` → `XsdTypeMapper.toXsdType`

read (ConnId → shadow)::
  `ZonedDateTime` → `XMLGregorianCalendar` (explicit conversion; passes the runtime type check) — in `ConnIdToUcfObjectConversion.convertAttributeValueFromConnId`

write & filters (shadow → ConnId)::
  `XMLGregorianCalendar` → `ZonedDateTime` — in `ConnIdUtil.convertValueToConnId`

So a connector may declare custom date attributes (and even the password date/interval
attributes below) as `ZonedDateTime` and midPoint will round-trip them.

=== Special attributes: `long` (epoch millis) is mandatory

midPoint does *not* support `ZonedDateTime` for the date specials it handles
specially — `pass:[__ENABLE_DATE__]`, `pass:[__DISABLE_DATE__]` and
`pass:[__LAST_LOGIN_DATE__]` — because their conversion is hardwired to `long`:

* Read: `convertEnableDate()` / `convertDisableDate()` / `convertLastLoginDate()`
  extract the value with `getSingleConvertedSimpleValue(attr, Long.class)`. A
  `ZonedDateTime` value is first converted to `XMLGregorianCalendar`, and
  `MiscUtil.castSafely(..., Long.class)` then fails with
  `SchemaException("Expected 'java.lang.Long' but got ...XMLGregorianCalendar")` —
  the whole object conversion fails (midPoint only produces a partial shadow with
  an error state).
* Write: `collectReplaceXMLGregorianCalendar()` always emits
  `XmlTypeConverter.toMillis(...)` — a `Long` — for `pass:[__ENABLE_DATE__]` /
  `pass:[__DISABLE_DATE__]`, no matter what the connector schema declares.
* The ConnId framework's own accessors (`AttributeUtil.getDateValue()` /
  `getEnableDate()` / `getPasswordExpirationDate()` via `getLongValue()`) and the
  standard `AttributeInfo`s also declare/expect `long.class`.

Declaring these specials as `ZonedDateTime` is legal at the framework level (the
type is whitelisted), but it breaks midPoint reads and violates the midPoint write
contract — use `long` epoch-millis (UTC) for them.

=== Password date/interval attributes: generic path

`pass:[__PASSWORD_EXPIRATION_DATE__]`, `pass:[__LAST_PASSWORD_CHANGE_DATE__]` and
`pass:[__PASSWORD_CHANGE_INTERVAL__]` are *not* special-cased by midPoint (they are
not in the `SpecialAttributes` capability list nor in the object-conversion
switch), so they flow through the generic attribute path — where `ZonedDateTime`
works as described above.

NOTE: Even on the generic path the value type must match the declared schema type:
a `Long` value in a `ZonedDateTime`-typed attribute (or vice versa) fails
midPoint's type-compatibility check.

.Practical rule
`pass:[__ENABLE_DATE__]`, `pass:[__DISABLE_DATE__]`, `pass:[__LAST_LOGIN_DATE__]`::
  `long` epoch-millis (UTC) — midPoint hard requirement

`pass:[__PASSWORD_EXPIRATION_DATE__]`, `pass:[__LAST_PASSWORD_CHANGE_DATE__]`, `pass:[__PASSWORD_CHANGE_INTERVAL__]`::
  `long` recommended (standard infos), `ZonedDateTime` works (generic path)

custom date attributes::
  `ZonedDateTime` (or `long`) — both fully supported

== Connector-Side Handling (Generic ConnId SPI)

=== Schema (`schema()`)

* Declare special attributes with the standard types and flags — reuse
  `OperationalAttributeInfos` / `PredefinedAttributeInfos` as the reference and
  only adjust flags (e.g. `NOT_RETURNED_BY_DEFAULT`, `NOT_READABLE`) to match
  what the resource actually supports.
* Declare `nativeName` for special attributes whenever the resource has a real
  attribute name (e.g. `dn` for `pass:[__NAME__]`, `entryUUID` for
  `pass:[__UID__]` in LDAP). midPoint prefers the native name over the
  generic `icfs:*` fallback items.
* Never declare `pass:[__UID__]` in the schema; it is not a storable attribute.
* Password attributes must be declared `NOT_READABLE` + `NOT_RETURNED_BY_DEFAULT`
  (a read-only password resource must then drop `NOT_READABLE` — but
  `NOT_READABLE` *requires* `NOT_RETURNED_BY_DEFAULT` per the flag-consistency
  rule; the standard `OperationalAttributeInfos.PASSWORD` is the safe default).
* Date attributes: use `long` (epoch millis, UTC), not `Date` (not a supported
  type) and not `ZonedDateTime` unless the whole connector consistently uses it
  (midPoint's legacy XSD expects `xsd:long` for the `icfs:` date attributes).

=== Objects (`get()`, `search()`, `create()`, `update()`, `sync()`)

* Every returned `ConnectorObject` must contain `Name` and `Uid` instances.
  If the resource has no separate internal id, UID and NAME may carry the same
  value (e.g. primary-key-based connectors).
* `create()` returns the new `Uid`. The UID must not be part of the created
  attribute set.
* Operational attributes may appear in the attribute set of `create()` /
  `update()` deltas to express state changes in a single operation (e.g.
  `pass:[__ENABLE__]=false` on create).
* `pass:[__PASSWORD__]` values are always `GuardedString`; never a `String`.
  The framework enforces this in both `Attribute` and `AttributeInfo`.
* `pass:[__CURRENT_PASSWORD__]` is a legacy pseudo-attribute for self-service
  password changes. The `OperationalAttributes` javadoc explicitly says not to
  use it with delta-based update operations — those have a first-class way to
  pass the old/current password.
* When a value exists but cannot be returned (e.g. a password), return the
  attribute with `AttributeValueCompleteness.INCOMPLETE` instead of omitting it:
  "the attribute exists and has at least one value, but the value is unknown".
  midPoint interprets an incomplete password as "password present, unknown".
* `pass:[__GROUPS__]` values are the `Uid` strings of group objects (object
  class `pass:[__GROUP__]`), not display names.
* `pass:[__AUXILIARY_OBJECT_CLASS__]` values are object class names known to the
  connector's schema.
* Errors that are really about a value not being acceptable (e.g. a password
  rejected by the resource's policy) should be reported with
  `InvalidAttributeValueException`, including the affected attribute names —
  midPoint maps a password-related `InvalidAttributeValueException` to a
  `PolicyViolationException`.

=== conndev Low-Code DSL

The conndev base (`com.evolveum.polygon.conndev`) exposes the built-in
attributes through a dedicated enum and type-resolution rules:

* `ConnIdBuiltInAttribute` (`build/ConnIdBuiltInAttribute.java`) — the registry
  of built-in attributes, each with an optional *forced type*:
** `UID` (`pass:[__UID__]`) and `NAME` (`pass:[__NAME__]`) — forced
   `String.class` (a hard ConnId constraint).
** `PASSWORD` (`pass:[__PASSWORD__]`) and `CURRENT_PASSWORD`
   (`pass:[__CURRENT_PASSWORD__]`) — forced `GuardedString.class`.
** `ENABLE`, `ENABLE_DATE`, `DISABLE_DATE`, `LOCK_OUT` — no forced type; the
   connector script must declare the ConnId type (`Boolean` / `Long`).
** Scripts reference the constants by importing the enum, e.g.
   `import com.evolveum.polygon.conndev.build.ConnIdBuiltInAttribute` and then
   `connId { name ConnIdBuiltInAttribute.UID }`.
* Mapping a protocol attribute to a built-in attribute:
** `attribute("id").connId().name(ConnIdBuiltInAttribute.UID)` —
   `AttributeBuilder.ConnIdMapping.name(ConnIdBuiltInAttribute)`
** or `connIdAttribute("UID", "id")` on the object class builder — only
   `"UID"` and `"NAME"` are supported there; it binds the built-in name to an
   existing protocol attribute.
* Type resolution (`rules/AttributeTypeResolutionRule.java`): a single
  `AttributeOnly` rule whose internal priority chain evaluates candidate
  sources in order — the first one with an answer wins. The *first* candidate
  is the built-in forced type: any attribute whose ConnId name is a
  `ConnIdBuiltInAttribute` keeps its forced type (`String` for
  `pass:[__UID__]` / `pass:[__NAME__]`, `GuardedString` for the password
  attributes) regardless of what the protocol mapping suggested. The remaining
  candidates, in order: reference attributes → `ConnectorObjectReference`,
  attributes with a `complexType` → `EmbeddedObject`, the protocol mapping's
  suggestion, and finally the type explicitly declared on the attribute (the
  guaranteed last word).
 * After the final type is decided, `AttributeTypeCoercionRule`
   (`rules/AttributeTypeCoercionRule.java`) pushes it into every protocol value
   mapping. When a mapping's native ConnId type differs from the final one,
   `JsonMapping.build()` wraps the mapping in a `ValueTypeOverrideMapping`
   (`schema/ValueTypeOverrideMapping.java`):
 ** A *default* mapping (derived from the JSON type / OpenAPI format) is bridged
    with a value conversion — supported overrides are same-type passthrough,
    numeric/`ZonedDateTime`-to-`String` (e.g. an `int64`-backed
    `pass:[__UID__]`) and `String`↔`GuardedString` (e.g. a JSON `string` or
    `password`-format mapping behind a `GuardedString`-forced attribute — the
    wire value stays a JSON string, the ConnId value a `GuardedString`), so any
    other combination (e.g. a JSON `string` mapping for a reference attribute)
    fails the schema build.
** A *custom* mapping (a user-supplied `implementation`) is never bridged: its
   `serialize`/`deserialize` closures own the wire↔ConnId conversion and produce
   the type from the connid section, not from the default JSON mapping, so the
   built mapping is only re-labeled to the final ConnId type
   (`ValueTypeOverrideMapping.asConnIdType`). This is how an attribute that the
   default mapping cannot bridge is supported — e.g. a reference attribute whose
   `deserialize` builds a `ConnectorObjectReference` from a JSON string
   (`json { type("string") implementation { deserialize { ... } } }`).
* Naming defaults: when nothing else claims `pass:[__NAME__]` (protocol-specific
  detection or an explicit `connIdAttribute("NAME", …)`), `NameDefaultsToUidRule`
  creates it as a copy of the `pass:[__UID__]` attribute. Protocol-specific
  built-in detection (e.g. the SCIM `id` → `pass:[__UID__]` mapping) belongs to
  the protocol framework, not to the conndev base. `FilterBasedSearchDispatcher`
  gives single-value `pass:[__UID__]`-equals filters special treatment
  (rewriting them via the `nameHint` when no filter implementation matches).

NOTE:: *Known DSL gap* — `ConnIdBuiltInAttribute` exposes UID, NAME, PASSWORD,
CURRENT_PASSWORD, ENABLE, ENABLE_DATE, DISABLE_DATE and LOCK_OUT.
`pass:[__FORCE_PASSWORD_CHANGE__]`, `pass:[__PASSWORD_EXPIRED__]`,
`pass:[__PASSWORD_EXPIRATION_DATE__]`, `pass:[__GROUPS__]`,
`pass:[__DESCRIPTION__]`, `pass:[__SHORT_NAME__]`,
`pass:[__LAST_LOGIN_DATE__]` and `pass:[__AUXILIARY_OBJECT_CLASS__]` are not
exposed as enum constants; scripts that need them must pass the special name
via `connId().name(...)` (e.g. `pass:[__FORCE_PASSWORD_CHANGE__]`) and declare
the type explicitly (per the catalog above).

== Gotchas and Edge Cases

* *UID ≡ NAME*: connectors whose object has no separate internal id may use the
  same value for both. midPoint then reuses one attribute definition for the
  primary identifier and does not double-map it.
* *Native name preference*: always declare `nativeName` for
  `pass:[__UID__]`/`pass:[__NAME__]` (and other specials) — otherwise midPoint
  falls back to the generic `icfs:uid`/`icfs:name` items, which the documentation
  explicitly discourages configuring.
* *`pass:[__FORCE_PASSWORD_CHANGE__]` / `pass:[__SHORT_NAME__]`*: not in midPoint's static
  special-name map; expose them via `nativeName` or expect them to be treated as
  ordinary `ri:` attributes.
* *`icfs` XSD quirks*: `lastPasswordChangeDate` / `passwordChangeInterval` are
  `xsd:string` in `resource-schema-3.xsd`; `uid` is read-only with
  `maxOccurs=1`.
* *`NOT_READABLE` ⇒ `NOT_RETURNED_BY_DEFAULT`*: the framework enforces this
  flag pairing; a "readable password" capability corresponds to dropping
  `NOT_READABLE` (keeping `NOT_RETURNED_BY_DEFAULT`).
* *Value completeness*: use `AttributeValueCompleteness.INCOMPLETE` for
  present-but-hidden values (passwords); omitting the attribute entirely means
  "no assumption possible".
* *Legacy vs. modern schema*: presence of `pass:[__ACCOUNT__]` /
  `pass:[__GROUP__]` object classes forces legacy naming
  (`CustomXxxObjectClass`, `account`/`group` local names).
* *Type drift risk*: because the framework does not validate the boolean/long
  types of most specials, a connector that returns e.g. `String` dates or
  `Integer` dates will pass ConnId but break midPoint reads with a
  `ClassCastException`-style failure or a `SchemaException` from the
  type-compatibility check. In particular, `ZonedDateTime` must not be used for
  the date specials — see the "Date Value Types" section.
* *conndev DSL gap*: only `UID`/`NAME` (`String`) and `PASSWORD`/
  `CURRENT_PASSWORD` (`GuardedString`) have forced types in
  `ConnIdBuiltInAttribute`; the remaining operational attributes must have
  their ConnId type declared explicitly in the script (`Boolean`, `Long`).
